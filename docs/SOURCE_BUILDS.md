# 词库来源重建与发布检查

日常开发使用已提交的词库，不需要重建。`npm run data:build` 和 `npm run data:manifest` 只在来源缓存完整、输入已复核时使用。缺少输入或核验失败不会覆盖已有发布包或来源清单。

## 固定输入与观察记录

`config/source-input-lock.json` 是独立的审核基线。初始 18 个文件的 SHA-256 和字节数沿用提交 `3bf40c8f6c0ea37d7cb9397645b3eca8343b55b8` 的历史来源清单，用于拒绝后续缓存修改；这不是新的上游真实性、版本或许可证明。`source_manifest.json` 继续记录来源和观察结果，重新生成它不会自动批准新输入。

当前仓库没有 Mikigo 的 `files_complete.tsv` 与引用文件、OEWN 已解压 JSON 的可信逐文件哈希。原始缓存也未包含在仓库中。需要补齐这些输入并完成以下复核，才能运行真实来源重建；不能用缺失文件、空字典或自行计算的哈希假装已核验。

1. 在独立、不发布的缓存中获取有明确版本与许可依据的原始来源。对照来源 URL、版本、原记录、页图/独立证据和许可，检查正文与文件集合；下载成功或哈希存在本身不代表审核完成。
2. 使用 `node scripts/source-pin-candidates.mjs <cache-root> <relative-file> ...` 检查候选字节数和 SHA-256。该命令只输出 `unreviewed-candidate`，不会写入可信 lock。Mikigo 必须包含 TSV 和它引用的全部文件；OEWN 必须包含实际消费的 `entries-*.json`、`noun.*.json`、`verb.*.json`、`adj.*.json`、`adv.*.json`，解压内容还应与已有固定哈希的原始 ZIP 核对。不能只固定 ZIP 后继续信任被改过的解压目录。
3. 完成复核后，将批准的相对路径、`sha256`、`bytes` 加入 lock 的 `files`，记录复核依据，移除对应的 `pending` 项。新增/更换 pin 是可审查的代码变更，不能由 `data:manifest` 自动接受；确认新 lock 没有漏掉原来源。
4. 设置 `PEP_VOCAB_SOURCE_CACHE` 并执行来源记录/词库重建、数据审计和受影响测试。核对稳定 ID、来源、权利字段及所有生成差异；改变 ID 或删除有效词条需要另行实现数据兼容迁移。

来源重建和候选哈希检查使用 Linux/WSL 环境，要求可用的 `/proc/self/fd`。其他平台可使用已提交词库开发应用，但不能降级为仅靠文件名核验的来源读取。

所有缓存路径都必须是相对路径。打开文件时禁止跟随末级软链，并检查实际打开句柄的真实路径仍在缓存根目录内，覆盖 `..`、绝对路径、目录组件软链及检查后替换的情况。句柄还必须是普通文件、字节数符合固定 pin 且不超过 256 MiB；读取严格限制为这些字节及一个用于检测增长的探测字节。同一句柄读取并通过固定哈希检查的字节再复制到私有临时快照，解析器只读该快照，因此核验后修改原缓存不会改变本次生成内容。

## 发布目录

发布只包含 `manifest.json`、`index.json` 和清单逐一声明的 `chunks/lexicon-NN.json`。审计、普通 `npm run build` 及构建产物检查共用完整目录检查：缺文件、额外文件/目录、软链、重复声明、条数/首尾 ID 不一致、非法发音字段或不安全权利标识都会失败。索引的所有发布字段（层级、范围、核心义、IPA、词性、裁剪后的来源定位和 flags）必须与已审计 chunk 的共同投影完全一致，不能仅凭 ID 匹配通过。

词库在同一父目录的新 staging 中生成并检查，通过后与原始提取记录、规范化记录、单元核对和审计报告一起交换；普通替换/写入失败会恢复旧输出。如果恢复本身因磁盘故障失败，保留恢复目录并明确报错。旧目录中的未声明文件会使替换失败，避免静默删除未知文件，需先调查来源。生成的旧 chunk 随成功的较小发布一起移除。目录和文件重命名之间存在很短的交换间隔，因此这是离线构建步骤，不应在生产静态服务目录上直接运行。原始教材和用户上传文件不会进入发布目录。
